# 最后一轮业务增强实施计划

**目标：** 完成审核驳回重提、拒单重派、幂等 SLA、验收返工和维修预约，完成审查后冻结业务范围。
**依据：** 用户本轮完整需求及当前源码、数据库检查。
**架构：** 扩展现有四张表，不增加业务表。OrderWorkflowService 负责新增动作和共用生命周期；原认证、评分算法、地图保持不变。
**技术：** 现有 Spring Boot / MyBatis Plus / Vue / TypeScript，无新依赖。由主代理直接执行。

## 决定与约束
- REJECTED → 原 ID 修改重提 → WAIT_AUDIT；WAIT_CONFIRM → REWORK_PENDING → 原维修员 ASSIGNED 或 WAIT_ASSIGN 重派。
- 智能 ASSIGNED 与人工 WAIT_ASSIGN 保留；新增 acceptedTime，响应后才能开始。历史已接单订单迁移为已响应。
- dispatchRound 隔离推荐批次；旧推荐不能跨轮确认。manual 记录明确标注人工指定，评分为空，不伪造评分。
- repairRound 标识维修记录；完成动作仅更新当轮记录。旧维修记录不覆盖。
- 预约用订单字段保存当前信息，用事件保存历史，version 拒绝旧页面确认；不阻塞正常维修。
- SLA 根据 LOW/NORMAL/HIGH 集中配置，派单响应与开始维修分别计时；数据库行锁串行检测，仅记录一次事件/通知。
- 通知与事件同事务提交；失败回滚，不留下“已通知但业务失败”或静默丢失的通知。
- 聊天读写与派单共用订单锁，旧维修员被替换后立即失去访问权限；新维修员只读其参与消息，管理员/学生保留完整历史。
