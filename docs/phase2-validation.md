## 真实HTTP与MySQL

`python3 backend/scripts/check_auth.py`：56项断言通过。

- 三账号正确密码返回token/角色/用户；响应无密码或哈希。
- 错密码和未知账号返回相同友好401；空密码、超长参数返回400。
- 三角色匿名接口401；3×3权限矩阵本角色200、其余403；管理员可访问管理员接口，学生不可访问。
- 有效JWT可获取当前用户；未创建session cookie。
- 伪造payload、错误签名、错误算法、无签名、过期、未来nbf、错误issuer、缺少exp、版本错误均401。
- 禁用用户不能登录，已签发token也拒绝；数据库角色变化即时影响授权，JWT中的旧role不被信任。
- 三角色退出成功后旧token401，新登录可用。
- 精确CORS来源和Authorization预检允许，其他来源拒绝。
- 数据库没有明文123456，仅存在user表，没有Phase3业务表。

初始化SQL再次执行后，用户id/账号/密码哈希/角色/状态/版本全部保持，未覆盖既有用户。验收临时修改student001状态/角色后已恢复。

## 前端生产代码状态流程

`npm run check:auth`：17项通过，执行实际Pinia、Axios、Router代码，连接真实后端；只以内存对象代替浏览器localStorage。

- 未登录跳登录页、错误密码不持久化。
- 学生/维修/管理员真实登录进入对应入口；跨角色路由回自身首页。
- 创建新的Pinia和路由模拟刷新，持久化token恢复后端可信身份。
- 退出清除token、返回登录页，后端拒绝旧token。
- 无效存储token被清除；暂时网络故障保留token，可重试恢复。
- 状态/路由检查无console警告。

`npm run check:session`：4项针对异步排序/跨标签状态的回归检查通过；使用控制响应顺序的Axios adapter，非真实HTTP。

- 旧会话迟到401不清除新登录。
- 请求token与显示的Pinia身份一致，其他标签更改storage不直接替换请求身份。
- 存储同步后旧user清空，再恢复后端身份。
- 旧退出请求迟到不清除新会话。

两个问题先以失败断言复现，再修复。只读代码评审发现的问题已修复并复核，未发现剩余Critical/Important。
